# 检索方案

> 管线第 ④ 步：把用户问题在向量库上检索，产出 top-k 命中与分数，供生成阶段拼上下文。
> 指标结果见 `验收复盘_混合重排.md`；向量库构建见 `向量化方案.md`。

## 1. 定位

```
… → 向量化 → 【检索（本步）】 → 生成
```

| 项 | 内容 |
|---|---|
| 输入 | 用户问题 + `data/chroma`（集合 `rag_chunks`）+ `data/chunks/*.chunks.jsonl`（混合路线需要 BM25 语料） |
| 输出 | top-k 命中列表 `{id, score, text, meta}`，其中 `meta` 含 `doc / section_path / start_block / end_block / start_page / end_page` |
| 代码 | `retrieval/search.py`（路线封装）、`retrieval/hybrid.py`（BM25 + RRF）、`retrieval/reranker.py`（重排） |

## 2. 两条检索路线

### 2.1 纯向量（`vector_only`，基线）

```
embed(query) → chroma 余弦检索 top-k
```

`score` = **余弦相似度**（chroma 返回 distance，取 `1 − distance`）。

### 2.2 混合候选 + 重排（`hybrid_rerank`，默认路线）

严格串行的一条链（下例数字对应评测用的 top-k ≤ 5，此时召回深度 `n = max(20, k+6) = 26`）：

```
① 向量检索      chroma 余弦 → top-26
② BM25 检索      jieba 分词 + rank_bm25 → top-26
③ RRF 融合      把 ① ② 的排名融合 → 排序
④ 取候选        RRF 排序后 top-20 ← 这就是「候选池」
⑤ 重排          DashScope qwen3.7-text-rerank 对候选打分
⑥ 取 top-k      按 relevance 降序取 top-k
```

`score` 在第 ⑤ 步被**替换为重排的 `relevance_score`**。因此两条路线虽然共用「分数」字段，
**语义不同**（余弦相似度 vs 相关性分），尺度也不同——这一点直接决定了拒答阈值必须分路线配置
（见 `生成方案.md`）。

## 3. 关键设计

**为什么用 RRF 而不是加权求和**

BM25 与向量检索的分数**量纲不可比**（前者是无界相关性分，后者是余弦相似度），直接加权求和需要先做归一化，
而归一化方式又会引入新的假设。RRF（Reciprocal Rank Fusion）只用**排名**：

```
score(d) = Σ_i  1 / (k + rank_i(d) + 1)      k = 60
```

排名靠前的文档在多个列表中同时出现时得分自然更高，无需调权重。

**BM25 补什么**

向量检索对**精确串**不敏感：专名、数字、版本号、活动名（如「S7 赛季」「+22」「晶核打金节」）。
BM25 基于词面匹配，正是补这一类查询的短板。

**重排为什么走 API**

本地 reranker（如 `bge-reranker`）依赖 `torch` / `onnxruntime`，本机存在 DLL 加载失败与崩溃问题；
因此改用 DashScope 的重排 API（`qwen3.7-text-rerank`），不引入本地模型依赖。

**候选深度参数**

`n = max(20, k + 6)` 决定两路召回各自取多少条进 RRF；`reranker.top_n = 20` 决定送进重排的候选数。
在 605 chunk 的语料上，26 条召回约占全库 4.3%。成本上：BM25 与向量检索**不影响成本**（`n` 只决定返回条数），
而**重排按 token 计费**（query + 全部候选正文），因此候选数是主要成本与延迟项。

## 4. 参数

| 参数 | 取值 | 说明 |
|---|---|---|
| 路线 | `hybrid_rerank`（默认）/ `vector_only` | 见 `run_rag.DEFAULT_MODE` |
| 召回深度 `n` | `max(20, k + 6)` | 两路各自送入 RRF 的条数 |
| 候选池 `top_n` | 20 | 送入重排的候选数 |
| RRF `k` | 60 | `score = Σ 1/(k + rank + 1)` |
| 评测 top-k | simple **3** / complex **5** | `scripts/_common.py` 的 `QA_K`；complex 每题含 2~4 个来源 |
| 距离度量 | cosine | 向量库 `hnsw:space=cosine` |

## 5. 代码结构

```
retrieval/
├─ search.py       # vector_search / make_search（按路线返回 search(query, k)）
├─ hybrid.py       # _tokenize / rrf_fuse / HybridSearch / build_hybrid_search
└─ reranker.py     # DashScopeReranker.rerank（top_n 取 min(候选数, 20)）
```

配套脚本：

| 脚本 | 用途 |
|---|---|
| `scripts/query_retrieval.py` | 检索冒烟：打印 top-k 的分数与**完整溯源坐标**（人工核对） |
| `scripts/eval_retrieval.py` | 按路线计算指标（simple: recall/MRR/P@1；complex: recall/precision） |
| `scripts/ablate_search.py` | 四路消融（混合候选+重排 / 混合候选 / 纯向量候选+重排 / 纯向量） |
| `scripts/calibrate_threshold.py` | 阈值（拒答值）校准：统计正/负类 top-1 分布并给建议值 |
| `scripts/eval_metrics.py` | 指标纯函数（无 API、无 IO，可单测） |

## 6. 指标口径（定义，不列结果）

对一题（来源集合 `S`，检索返回文档序列 `D`，截取前 `k` 个）：

| 指标 | 定义 |
|---|---|
| `recall@k` | `|unique(命中来源)| / |S|` —— 同来源的多个 chunk 只计一次 |
| `precision@k` | `|{d ∈ D_k : d ∈ S}| / k` |
| `P@1` | `D₁ ∈ S` 时为 1 |
| `MRR` | 第一个属于 `S` 的文档排名的倒数 |

- 单来源题（`|S| = 1`）时 `recall@k` 退化为 0/1 命中，因此两套评测集可共用同一套函数。
- **多来源题不计算 P@1 / MRR**：不存在「唯一正确答案」。
- 不可答题（`S` 为空）不参与上述指标，仅用于拒答统计。
- 辅助参照：`any-hit`（至少命中一个来源的题目占比）、`all-hit`（来源被完全覆盖的题目占比）。

## 7. 已知限制

- **候选深度未做消融**：`26`（召回深度）与 `20`（候选池）是启发式取值，未验证「更浅/更深」的收益差异；
  在小语料上把 20 压到 10 左右可能不大损召回，但缺乏数据支撑。
- **检索结果存在运行间小幅波动**：同集同 k 重复检索时，top-k 内偶有顺序或边界差异，
  主要来自 embedding 服务与余弦并列排序。
- **多跳能力有限**：单轮 top-k 检索对「需要整合 2~4 篇来源」的问题覆盖不全，
  缺口集中在跨文档题。
- **BM25 语料来自切片产物**：若 `data/chunks` 缺失，混合路线无法构建 BM25（脚本会给出明确的构建指引）。
