# 检索方案

> 管线第 ④ 步：把用户问题在向量库上检索，产出 top-k 命中与分数，供生成阶段拼上下文。
> 指标结果见 `验收复盘_混合重排.md` 与仓库根的 `metrics.json`；语料侧产物见 `向量化方案.md`。

## 1. 定位

```
… → 语料侧产物（data/chroma + data/bm25） → 【检索（本步）】 → 生成
```

| 项 | 内容 |
|---|---|
| 输入 | 用户问题 + `data/chroma`（集合 `rag_chunks`）+ `data/bm25/bm25_corpus.pkl`（BM25 语料侧产物；缺失时回退读 `data/chunks/*.chunks.jsonl` 现场分词构建） |
| 输出 | top-k 命中列表 `{id, score, text, meta}`，其中 `meta` 含 `doc / section_path / start_page / end_page` |
| 代码 | `retrieval/search.py`（路线封装）、`retrieval/hybrid.py`（BM25 + RRF + 产物加载）、`retrieval/reranker.py`（重排） |

## 2. 语料侧产物（构建一次，查询期只读）

两条检索路线各有一份**语料侧产物**，与切片产物对称，构建后查询期不再重做语料侧的重活：

| 产物 | 构建脚本 | 内容 | 查询期做什么 |
|---|---|---|---|
| `data/chroma/` | `scripts/run_vectorize.py` | 每块一条 `向量 + document(=text) + metadata(溯源)` | query 嵌入（**1 次 API**）→ 余弦 top-k |
| `data/bm25/bm25_corpus.pkl` | `scripts/run_bm25_build.py` | `ids + BM25Okapi(doc_freqs/doc_len/avgdl/idf) + texts + meta` | query **jieba 分词一次** → `get_scores()` → 分 > 0 的 top-n |

- BM25 产物**不存语料分词结果**：`get_scores()` 只用 BM25Okapi 内部统计量，存了没人读。
- 构建脚本与查询期**必须共用同一个 `retrieval.hybrid.tokenize`**：产物里的 `idf/doc_freqs` 是按它切出的词表算的，
  换一套分词会让 query 的词对不上词表、分数静默变差。
- **不做指纹校验、不做失效逻辑**：与 `data/chroma` 同等对待，语料或切片变了就重跑构建脚本。
- 实测（607 块）：产物 0.89 MB；加载 10–16 ms vs 现场分词构建 391–409 ms。

## 3. 两条检索路线

### 3.1 纯向量（`vector_only`，基线）

```
embed(query) → chroma 余弦检索 top-k
```

`score` = **余弦相似度**（chroma 返回 distance，取 `1 − distance`）。

### 3.2 混合候选 + 重排（`hybrid_rerank`，默认路线）

```
① 向量检索      chroma 余弦 → top-n
② BM25 检索      jieba 分词(query) + rank_bm25 → top-n
③ RRF 融合      把 ① ② 的排名融合 → 排序
④ 取候选        RRF 排序后取 K 条 ← 这就是「候选池」
⑤ 重排          DashScope qwen3.7-text-rerank 对候选打分（参数 top_n = min(候选数, 20)）
⑥ 取 top-k      按 relevance 降序取 top-k
```

其中 `K = max(20, k + 6)`（`search.make_search` 传给 `HybridSearch.search` 的候选数）、
`n = max(20, K + 6)`（两路各自送入 RRF 的条数）。评测用 `k = 5` 时：`K = 26`、`n = 32`、重排 `top_n = 20`，最终取 top-5。

`score` 在第 ⑤ 步被**替换为重排的 `relevance_score`**。因此两条路线虽然共用「分数」字段，
**语义不同**（余弦相似度 vs 相关性分），尺度也不同——这一点直接决定了拒答阈值必须分路线配置
（见 `生成方案.md`）。

## 4. 关键设计

**为什么用 RRF 而不是加权求和**

BM25 与向量检索的分数**量纲不可比**（前者是无界相关性分，后者是余弦相似度），直接加权求和需要先做归一化，
而归一化方式又会引入新的假设。RRF（Reciprocal Rank Fusion）只用**排名**：

```
score(d) = Σ_i  1 / (k + rank_i(d) + 1)      k = 60
```

排名靠前的文档在多个列表中同时出现时得分自然更高，无需调权重。

**BM25 补什么**

向量检索对**精确串**不敏感：专名、数字、版本号、活动名（如「S7 赛季」「+22」「晶核打金节」）。
BM25 基于词面匹配，正是补这一类查询的短板。

**重排为什么走 API**

本地 reranker（如 `bge-reranker`）依赖 `torch` / `onnxruntime`，本机存在 DLL 加载失败与崩溃问题；
因此改用 DashScope 的重排 API（`qwen3.7-text-rerank`），不引入本地模型依赖。

**成本结构**

`n` / `K` 只决定返回条数，向量检索与 BM25 都**不按条计费**；而**重排按 token 计费**（query + 全部候选正文），
因此候选池大小是主要的成本与延迟项。607 chunk 的语料上，26 条候选约占全库 4.3%。

## 5. 落盘产物与离线流程（重要）

**检索只跑一次、落盘；指标与阈值都离线读这份快照**，避免"同一份报告的数字来自不同次检索"：

```
scripts/retrieval_pass.py          ← 唯一调检索 API 的脚本（embedding + rerank）
   └─► data/eval/retrieval_{route}.jsonl
        每题一行：{qid, set, answerable, route, k, hits:[{chunk_id, doc, section_path, page, score}]}
        **不存片段正文**（需要正文时按 chunk_id 回 data/chunks 取，judge 就是这么做的）
              │
              ├─► scripts/eval_retrieval.py       离线算检索指标（零 API，不落盘）
              └─► scripts/calibrate_threshold.py  离线算拒答阈值分布与权衡表
                    └─► data/eval/threshold_{route}.json
```

约定：

- **`retrieval_pass` 与生成阶段各自检索一次**：生成（`gen_answers`）要用**定稿阈值**现场决定是否拒答，因此它会自己再检索；
  **检索指标一律以快照为准**（两条链路不是同一次运行，存在运行间小幅波动）。
- 要重算指标/阈值，就**先重跑 `retrieval_pass`**——不保留"现场重算"路径，避免两套口径。
- `k` 两集统一取 `_common.QA_K`（当前都 = 5）。

## 6. 参数

| 参数 | 取值 | 说明 |
|---|---|---|
| 路线 | `hybrid_rerank`（默认）/ `vector_only` | 见 `run_rag.DEFAULT_MODE` |
| 召回深度 `n` | `max(20, K + 6)` | 两路各自送入 RRF 的条数（k=5 时 32） |
| 候选池 `K` / `top_n` | `max(20, k+6)` / `min(候选数, 20)` | 送入重排的候选数（k=5 时 26 / 20） |
| RRF `k` | 60 | `score = Σ 1/(k + rank + 1)` |
| 评测 top-k | **两集统一 5** | `scripts/_common.py` 的 `QA_K`；complex 每题含 1~4 个来源 |
| 距离度量 | cosine | 向量库 `hnsw:space=cosine` |

## 7. 代码结构

```
retrieval/
├─ search.py       # vector_search / make_search（按路线返回 search(query, k)）
├─ hybrid.py       # tokenize / rrf_fuse / HybridSearch（含 from_artifact）/ load_artifact / build_hybrid_search
└─ reranker.py     # DashScopeReranker.rerank（top_n 取 min(候选数, 20)）
```

配套脚本：

| 脚本 | 用途 |
|---|---|
| `scripts/run_bm25_build.py` | 构建 BM25 语料侧产物 `data/bm25/bm25_corpus.pkl`（纯本地，不调 API） |
| `scripts/retrieval_pass.py` | **检索 pass**：跑指定路线并落快照 `data/eval/retrieval_{route}.jsonl`（唯一调检索 API 的入口） |
| `scripts/eval_retrieval.py` | **离线**读快照算指标（simple: recall/MRR/P@1；complex: recall/precision） |
| `scripts/calibrate_threshold.py` | **离线**读快照标定拒答阈值（正/负类 top-1 分布 + 阈值区间权衡表） |
| `scripts/ablate_search.py` | 四路消融（混合候选+重排 / 混合候选 / 纯向量候选+重排 / 纯向量）；本轮未复验 |
| `scripts/eval_metrics.py` | 指标纯函数（无 API、无 IO，可单测） |

```powershell
# 检索 pass（两条路线，落快照）

# 指标 / 阈值（都离线读快照）
.venv_rag311\Scripts\python.exe -m scripts.eval_retrieval --mode hybrid_rerank --detail
.venv_rag311\Scripts\python.exe -m scripts.calibrate_threshold

# 消融（本轮未复验；会显著增加 API 调用量）
.venv_rag311\Scripts\python.exe -m scripts.ablate_search
```

## 8. 指标口径（定义，不列结果）

**文档级口径**：判定「召回片段**所属文档**是否在该题 `sources` 里」。对一题（来源集合 `S`，检索返回的文档序列 `D`，截取前 `k` 个）：

| 指标 | 定义 | 计数单位 |
|---|---|---|
| `recall@k` | `|unique(命中来源)| / |S|` | **文档**（同来源的多个 chunk 只计一次） |
| `precision@k` | `|{d ∈ D_k : d ∈ S}| / k` | **片段** |
| `P@1` | top-1 片段所属文档 ∈ `S` 时为 1 | 文档 |
| `MRR` | 第一个所属文档 ∈ `S` 的片段排名的倒数 | 文档 |

- 报告口径：`simple` 报 `recall@k / MRR / P@1`；`complex` 报 `recall@k / precision@k`
  （函数对两集都算四项，只是多来源下 P@1/MRR 不宜作结论）。
- 单来源题（`|S| = 1`）时 `recall@k` 退化为 0/1 命中，因此两集可共用同一套函数。
- **不可答题（`S` 为空）不参与上述指标**：跳过、**不补 0**（补 0 会系统性拉低 recall）；
  分母是 **54 道可答题**。它们只用于**阈值校准**（负类样本）与**拒答统计**。
- 辅助参照：`any-hit`（至少命中一个来源的题目占比）、`all-hit`（来源被完全覆盖的题目占比）。

## 9. 已知限制

- **候选深度未做消融**：`32`（召回深度）与 `20`（候选池）是启发式取值，未验证「更浅/更深」的收益差异。
- **检索结果存在运行间小幅波动**：同集同 k 重复检索时，top-k 内偶有顺序或边界差异，
  主要来自 embedding 服务与余弦并列排序；指标以落盘快照为准正是为了规避这一点。
- **多跳能力有限**：单轮 top-k 检索对「需要整合 1~4 篇来源」的问题覆盖不全，缺口集中在跨文档题
  （complex 全覆盖 16 题答案正确率 0.781 vs 部分覆盖 10 题仅 0.350）。
- **BM25 产物与切片产物一致性无校验**：不存指纹，语料或切片变更后若忘记重跑 `run_bm25_build`，
  检索会静默用到旧词表（本项目按"变了就重跑"的约定处理，与 `data/chroma` 同等）。
