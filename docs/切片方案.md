# 切片方案

> 管线第 ② 步：把数据准备产出的结构化语料组装成**适合向量化与检索**的最小单元（chunk）。

## 1. 定位

```
提取 → 清洗 → 【切片（本步）】 → 向量化 → 检索 → 生成
```

| 项 | 内容 |
|---|---|
| 输入 | `data/processed/*.jsonl`（每行一个 `Block`，`kind = heading / para / table`） |
| 输出 | `data/chunks/*.chunks.jsonl` |
| 代码 | `chunking/chunker.py`（核心）、`scripts/run_chunking.py`（编排 + 统计） |

切片器**直接读 jsonl 的 `kind` 判边界**，不重新解析源文档，也不从 Markdown 反推结构。

## 2. 核心思路：结构感知，而非固定大小

数据准备保住 `heading / para / table` 结构，目的就是让切片能沿语义边界切，
而不是把一句话或一张表从中间劈开。第一原则是**尊重 Block 边界**。

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 固定大小 + 重叠 | 按字符数切窗段 | 均匀、简单、普适 | 切碎语义/表格/标题，浪费 Block 结构 |
| B 纯结构优先 | 只按标题/段落/表格切，不二次切 | 语义完整 | 块大小严重不均，超长章节始终超长 |
| **C 混合（本实现）** | 结构优先打底 + 超长按句切 + 过短融合 | 兼顾语义与大小 | 规则稍多，需兜底 |

## 3. 具体规则

1. **标题为一级边界**：遍历时维护**标题栈**得到 `section_path`；每个 `heading` 开启新 section，
   嵌套标题按 `level` 截断栈再入栈，形成正确层级。
2. **表格不可拆分**：`table` 整体成块（表格常是事实型问题的答案所在）。
3. **段落按目标大小聚合**：section 内段落依序累积到 `chunk_size` 即切，切点落在**段与段之间**；
   块内段落用**换行**连接，保留段落边界。
4. **超长兜底——按句切**：单段超过 `chunk_size` 时先按句边界切分，**绝不在句中拦腰截断**；
   仅当单句本身极长（无句边界）才允许硬放。
5. **重合（overlap）**：大小驱动的切点处，下一块开头补上一块的**尾部整句**，防止关键语义/问句被切在两块之间。
   重合**收敛到句边界**，因此可能略大于设定比例。
6. **过短融合**：section 末尾若残留 `< min_chunk` 的碎片，**一次性**回并进前一块；
   表格保持整体，不并入其他块。

## 4. 关键参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `chunk_size` | 300 | 目标块大小（字符） |
| `min_chunk` | 100 | 小于该值触发融合 |
| `overlap_ratio` | 0.15 | 相邻块重合比例（实际按句边界取整，`int(300×0.15)=45` 字） |
| 句边界 | `。！？；;!?\n` | 切分优先位置 |
| `attach_heading` | `True` | 把 `section_path` 拼进 `text`（增强召回） |

> 字符数与 token 数近似但不等价；本阶段用字符数作为可读、易验证的主单位。

## 5. 产物：chunk 结构

真实示例（`examples/9月2日更新公告…_chunks.jsonl` 首块）：

```json
{
  "id": "chunk_000001",
  "doc": "9月2日更新公告丨常规服团本活动开启 赛季服强化突破功能上线",
  "section_path": ["9月2日更新公告丨常规服团本活动开启 赛季服强化突破功能上线", "常规服"],
  "text": "9月2日更新公告丨常规服团本活动开启 赛季服强化突破功能上线 > 常规服\n亲爱的冒险者：\n为了给冒险者们提供更好的体验……",
  "rows": [],
  "start_block": 2, "end_block": 5,
  "start_page": 1, "end_page": 1
}
```

- `text` —— **真正用于向量化与检索的字符串**（含标题前缀、overlap 前缀、段落换行）。
- `id` —— 全局递增序号 `chunk_{序号:06d}`，自 `chunk_000001` 起（不携带文档标题）。
- `doc` / `section_path` / `start_block` / `end_block` / `start_page` / `end_page` —— 溯源坐标。
- `rows` —— 表格行的原始结构（非表格块为空数组）。

> **原文档与数据准备产物一律不改**：切片是本步新增的下游产物，单独落盘；
> 每个 chunk 凭 `doc + section_path + start/end_block(+page)` 可回溯回源文档与页码。

当前语料：1782 块 → **605 chunk**（数字见 `metrics.json`）。

## 7. 已知限制

- **重合比例会被整句取整放大**：句子较长时，重合前缀可能超出设定比例（为不切半句）。语义复用优先。
- **表格不做智能拆分**：超长表格整体成块，不做「按行组切」（当前语料不含真表格，暂未触发）。
- **caption / 图表说明**暂未与相邻表格智能合并，仅靠「过短碎片回并」兜底。
- 提取阶段对**强装饰版式**（逐字排版、重复水印）的标题识别是启发式，切片层如实承接
  （相关修复见 `数据准备方案.md`）。

## 8. 设计取舍

**为什么先做结构感知、不直接上语义切分（semantic chunking）**

语义切分的做法是：切成句 → 逐句嵌入 → 计算相邻句相似度 → 在相似度骤降处定边界。它擅长**无结构长文**，
但需要先有一遍嵌入、阈值抖动大、且与切片解耦性差。本项目选择先做结构感知：免费、确定、复用
`Block.kind` 的显式边界、与向量化解耦、易调试；语义切分可作为后续增强，只对「无结构长段落流」启用。

> 补充：入库检索用的向量必须「切片在前、嵌入在后」——embedding 是按**文本单元**计算的，
> 整篇文档的向量无法反推各片段向量；语义切分也只是"用向量找边界"，不是"切向量"。

**chunk 字段与生产通用做法的关系**

- 与生产一致的骨架：`text` + `id` + `metadata`（对应 LangChain `Document`、LlamaIndex `TextNode` 等）；
  标题既拼进 `text` 又存 `section_path`（检索友好 + 可溯源）。
- 相对自研的部分：用 `start/end_block`（Block 下标）而非 `start_char/end_char`（源文档字符偏移）。
  后者更通用（任意工具都能据此切回原文），但需要在数据准备阶段维护一份规范文本坐标轴；
  本项目以 `doc + page + section_path` 组合实现等价回溯。

## 9. 一句话总结

> 切片 = **以标题为一节边界、表格为整体单元，段落按目标大小聚合，超长按句切、过短回并，
> 并在切点附句边界重合**。核心是利用 `kind` 语义标签保住语义边界，让每个 chunk 都是
> 「语义自洽、可独立回溯原位置」的检索单元。
