# RAG 第二部分 · 切片：方案与代码实现

> 目标：读取数据准备产出的结构化语料 `data/processed/*.jsonl`(每行一个 `Block`，含 `heading/para/table`)，
> 进一步把它组装成**适合向量化 + 检索**的最小单元(chunk)。本文档给出方案设计说明与配套代码。

---

## 1. 切片的定位

```
提取 → 清洗 → 【切片(本阶段)】 → 向量化 → 检索 → 评估
```

- **输入** = `data/processed/*.jsonl`：数据准备的「真输出」，每行一个 `Block`(`kind=heading/para/table`)。
- **任务** = 在「语义完整的块」基础上，组装出**可以被 embedding + 检索**的最小单元(chunk)。
- **不重解析源文档**：切片器直接读 jsonl 的 `kind` 判边界，避免重复提取、也避免从 Markdown 反推结构。

## 2. 核心思路：结构感知(semantics-aware)，而非固定大小

数据准备花大力气保住 `heading/para/table` 结构，目的就是让切片能**沿着语义边界切**，
而不是把一句话、一张表从中间劈开。所以第一原则是：**尊重 Block 边界**。

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 固定大小+重叠 | 按字符数切窗段，相邻重叠 | 均匀、简单、普适 | 会切碎语义/表格/标题，违背 Block 设计初衷 |
| B 纯结构优先 | 只按标题/段落/表格切，不二次切 | 语义完整 | 块大小严重不均，超长章节始终超长 |
| **C 混合(本实现)** | 结构优先打底 + 超长按句切 + 过短融合 | 兼顾语义与大小 | 逻辑稍复杂，需兜底规则 |

采用 **C**：把 Block 的结构价值用起来，同时用「按句切分」兜住零星超长内容。

## 3. 具体规则

1. **标题为一级边界**：遍历 Block 时维护一个**标题栈**(得到 `section path`)；每个 `heading` 开启一个新 section，
   后续段落/表格归属该 section。嵌套标题按 level 截断栈再入栈，从而形成正确的层级。
2. **表格不可拆分**：`table` 作为一个整体单元成块，绝不切成两半(表格是事实型问题的答案所在)。
3. **段落按目标大小聚合**：section 内段落依序累积到目标大小 `chunk_size`，到达即切——切点落在**段与段之间**(语义边界)。
   块内段落用**换行**连接，保留段落边界，避免多段被无分隔粘连。
4. **超长兜底——按句切**：单个段落超过 `chunk_size` 时，先按句边界(。！？；;!?\n)切成若干组，
   **绝不在句中拦腰截断**；只有一句话本身极长(无句边界)才允许硬放。
5. **重合(overlap)**：大小驱动的切点处，下一段开头补上上一段的**尾部**(整句)作为重合前缀，防止关键语义/问句被切在两块之间。
   说明：重合总是**收敛到句边界**，不会把句子切一半，因此可能略大于设定的比例。
6. **过短融合**：section 末尾若有 `< min_chunk` 的碎片段，**一次性**回并进前一块，避免出现几个字的废块；
   表格保持整体性，不并入别块。

## 4. 关键参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `chunk_size` | 300 | 目标块大小(字符)；后续按 embedding 模型/查询长度调 |
| `min_chunk` | 100 | 小于则触发融合 |
| `overlap_ratio` | 0.15 | 相邻块重合比例(实际按句边界取整) |
| 句边界 | `。！？；;!?\n` | 切分优先在这些位置 |
| `attach_heading` | True | 把 `section_path` 拼进 text(增强召回) |

> 说明：中文里「字符数」与「token 数」近似但不等价；向量化阶段应以实际 embedding 模型为准。
> 本阶段先用字符数作为可读、易验证的主单位，保留后续 token 化的扩展点。

## 5. 产物：每个 chunk 的结构

```json
{
  "id": "chunk_000123",
  "doc": "sample3_vehicle",
  "section_path": ["公务用车管理规定", "一、适用范围"],
  "text": "公务用车管理规定 > 一、适用范围\n本规定适用于公司所有正式员工作业用车的申请与审批。",
  "rows": [],
  "start_block": 2, "end_block": 3
}
```

```json
{
  "id": "chunk_000124",
  "doc": "sample3_vehicle",
  "section_path": ["公务用车管理规定", "二、申请流程"],
  "text": "公务用车管理规定 > 二、申请流程\n车型 | 核载 | 用途\n商务车 | 7 座 | 接待\n货车 | 2 吨 | 运输",
  "rows": [["车型", "核载", "用途"], ["商务车", "7 座", "接待"], ["货车", "2 吨", "运输"]],
  "start_block": 6, "end_block": 6
}
```

- `text` = **真正拿去向量化 + 检索的字符串**(含标题前缀、含 overlap 前缀、段落边界换行)。
- `rows`(表格) / `section_path` / `start_block` / `end_block` = **元数据**，用于溯源、展示、评估。
- （2026-08 精简：`kind_comp`/`char_len`/`overlap` 已从 chunk 移除——纯展示/统计/调试，后段不消费；`char_len` 改用 `len(text)` 现算。`overlap` **文本前缀仍在**，只是不再存布尔标记。）
- （2026-08 id 方案A：`id` 改用**全局递增短键** `chunk_{序号:06d}`，不再携带文档标题；完整标题/溯源放在 `doc`/`section_path`/`start_block`/`end_block`。）

> 回答记忆里的疑问：**原文档与数据准备产物一律不动**；切片是本阶段新增的**下游产物**，
> 单独落盘到 `data/chunks/*.chunks.jsonl`。每个 chunk 通过 `doc` + `section_path` + `start/end_block` 可回溯回源文档。

## 7. 已知限制与后续

- **重合比例会被整句「取整」放大**：当句子较长时，重合前缀可能超出设定比例(为不切半句)。
  后续若需更严格，可改为「按词/按字符」重叠并放宽不切句约束，或接受——语义复用优先。
- **无结构文档(txt)**没有标题，整篇归入单一 section，靠段落聚合+超长按句切兜底。
- **md 列表被压平成一行**(数据准备的已知薄弱点)会在切片层随之延续；去重与列表结构保留留待后续版本。
- **caption/图表说明**暂未与相邻表格智能合并；当前仅做「过短碎片回并」。
- **PDF 换行产生的多余空格**(如「这片 厚土」)来自提取阶段 `" ".join(text.split())` 把文字层换行统一成了空格，
  是数据准备的已知局限，切片层如实地承接。后续可改进提取：对 CJK 相邻字符跨行时不插入空格。

## 8. 一句话总结

> 切片 = **以标题为一节边界、表格为整体单元，段落按目标大小聚合，超长按句切、过短回并，
> 并在切点附句边界重合(overlap)**。核心是利用 `kind` 语义标签保住语义边界，让每个 chunk 都是
> 「语义自洽、可独立回顾原位置」的检索单元。

## 9. 疑问与回答：本项目方案 vs 真实生产环境

> 本节整理开发过程中提出的疑问与回答，聚焦「本项目采取的方案」与「真实生产环境」的异同。相似/递进的问题归为一组。

### 9.1 能否「先向量化、再切片」？→ 语义切分与生产实践

**疑问**：能不能先给整篇向量化，再切片？

**回答**：分两种理解。
- **入库检索用的向量**必须「切片在前、嵌入在后」。embedding 是**按每个文本单元**算的，检索需要的是**片段向量**；整篇文档的向量**切不开、也反推不出**各片段向量。所以顺序只能是 切片 → 逐块向量化入库。
- 但存在一种真的「先向量化、再定切点」的技法——**语义切分(semantic chunking)**：切成句 → 逐句嵌入 → 算相邻句相似度 → **相似度骤降处 = 语义断层**(话题变了) → 据此合并成 chunk。它是「**用向量找边界**」，不是「切向量」。

**与生产对比**：生产上通常把「结构感知」与「语义感知」当作两路互补信号——
- 结构感知用标题/表格的**显式边界**(正是本项目的做法，复用 Block 的 `kind`)；
- 语义感知用 embedding 相似度，擅长**无结构长文**(如 LlamaIndex `SemanticSplitter`、LangChain `SemanticChunker`)。
两者常结合，而不是二选一。

**本项目取舍**：MVP 用结构感知——免费、确定、复用我们的 Block 结构、与向量化解耦、好调试；语义切分留作**第二版增强**，在向量化跑通后复用同一个 embedder，且只对「无结构长段落流」启用，以降低切分阈值抖动。这也正呼应了「待解决问题」里那条：无结构文档靠段落聚合 + 超长按句切兜底。

### 9.2 这个 chunk 结构是生产标准吗？→ 与生产环境对比(含字符偏移)

**疑问**：这个 `Chunk` 结构是真实项目的标准，还是仅为适配「上一步数据准备的 Block」？

**回答**：两者都有一点，分两层。

**① 与生产一致的骨架**：
- `text` + `id` + `metadata` —— 对应 LangChain `Document`(page_content+metadata)、LlamaIndex `TextNode`、Unstructured 元素类型的通用做法。
- `kind_comp` 的 `para/table` 语义 —— 类似 Unstructured 的 `element.type`(结构保留型 RAG 的做法)。
- 标题上下文既拼进 `text` 又存成 `section_path` —— 检索友好 + 可溯源，算最佳实践。

**② 相对「自研/贴 Block」的部分**：
- `start/end_block`(Block 下标)、`rows`(表结构)、`overlap`/`char_len`(诊断用)。

**什么是字符偏移**：`start_char`/`end_char` 指向源文档**文本坐标**里的起止位置(数第几个字)，任意工具、模型、人眼都能据此切回原文；比只有「我们」认识的 Block 下标更通用。所以生产常用 `start_char/end_char`，或 `source_uri + page + chunk_index`。

**生产向量库一行(对照我们的 Chunk)**：
```
{ id, vector, text, metadata: { source, doc_id, chunk_index, heading_path, type, start_char, end_char, ... } }
```
本项目的 Chunk 基本是这一行**去掉 `vector`、并把区块下标换成字符偏移**的前置版本。

**递进(生产化动作)**：第三部分(向量化)把 `Chunk` 映射成这一行——加 `vector`、`start/end_block` → `start/end_char`、补 `chunk_index`，`section_path`/`rows` 收进 metadata。届时一并算好每份文档的规范文本，字符偏移就有了坐标轴。（2026-08：`kind_comp` 已移除，不再进 metadata。）

### 9.3 样例太小，够不到 chunk_size？→ 参数校准与真实语料

**疑问**：示例几乎都是小文件，切片达不到 `chunk_size=300` 的阈值，是不是没意义？

**回答**：对，这批样例是给「提取」阶段做**边界夹具**用的(页眉页脚/空行/全角空格等噪音)，不是真实语料。因此切片的「聚合到 300 / 超长按句切 / 重合 / 融合」要靠**合成长文本自测**验证(见 `scripts/selftest_chunker.py`)，而非样例。

**关于参数**：`chunk_size=300` 是**参数，不是铁律**。它该怎么定，要等有真实数据、并确定 embedding 模型与查询上下文长度后才有意义。生产上通常会按**语料长度分布 + embedding 上下文窗口 + 查询粒度**来校准，而不是拍脑袋定一个固定值。

**递进**：已用 3 份真实文档(`示例1.docx` 结构型、`示例2.pdf`/`示例3.pdf` 文本型)跑通并切出真实 chunk；真实场景随之暴露了提取阶段的缺陷（PDF 换行加空格等，见第 7 节与 `docs/问题与处理记录.md`）。这正说明「用小样例验证机制、用真实数据校准参数」的工程路线。
