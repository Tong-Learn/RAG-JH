## A. 已处理（本次会话完成）

### A1.【提取】正文「换行切段」—— 核心修复
| 字段 | 内容 |
|---|---|
| 问题 | 公告类 PDF 在 PyMuPDF 里**一行 = 一个 text block**；旧提取只在单个 block 内合并行，导致**每行生成一个 para Block**，完整句子/段落被换行拆成多行。 |
| **影响** | ① 数据准备产物 jsonl/md 正文碎成**一行一段**；② 切片再把碎行用 `\n` 拼进 chunk → **chunk 内句子被换行拦腰割裂** → 向量按不连贯文本编码 → **语义连贯性下降，检索召回不集中**。这是本次最伤检索质量的一条。 |
| 解决方案 | `extract_pdf` 改用 **y-间距段落合并**：新增 `_estimate_line_h`（估正文行高）、`_merge_para_lines`（按 y 间距 ≤1.6×行高=同段合并，否则换段）、`_join_para_line_parts`（CJK 直连、仅 ASCII-ASCII 补空格）。**先判标题/表格再合正文**——标题/表格只作边界（`flush_para`），绝不并入段落。 |
| 处理效果 | para 块数：4月15日 31→13、4月8日 78→26、7月8日 150→54；chunk[0] 的完整句子**不再被 `\n` 割裂**；chunk 数 307→311→338（标题恢复后更多）。检索评估 precision@3 由 0.618→0.724。 |
| 状态 | ✅ 已修 |

### A2.【提取】文档标题被当「页眉」误删 + 跨行残片
| 字段 | 内容 |
|---|---|
| 问题 | 旧 `header_margin=60` 把顶部 y<60 的行当页眉剔除 → 文档标题主体（如 y≈42 的 `4月15日…钢铁洪流」来`）被删，只剩换行残尾 `袭` 一个 1 字 heading；同时真正该滤的文章元数据行（y≈90）却没删。 |
| 影响 | 标题作为溯源 `section_path` 的根节点缺失/残缺，展示与定位混乱。 |
| 解决方案 | **放弃 y-margin 页眉/页脚机制**（`_line_info`/`extract_pdf` 移除 `header_margin/footer_margin`）；只保留 cleaner 里**领域无关**的页码/独立数字过滤（`第X页/共Y页`、纯数字行）。**不做**领域正则（会过拟合到「晶核CoA」语料）。 |
| 处理效果 | 27 份文档中 **26 份标题恢复为完整 heading**；RAG `section_path` 现含完整标题（如 `8月19日… > 解除转职限制`）；评估 precision@3 提升。 |
| 状态 | ✅ 已修 |

### A3.【切片/向量化】chunk 与 chroma 元数据字段冗余
| 字段 | 内容 |
|---|---|
| 问题 | Chunk 带 `kind_comp/char_len/overlap` 三个**后段不消费**的字段；`kind_comp` 是 dict，入库要 `json.dumps`，徒增一次转换；`char_len` 可由 `len(text)` 派生。 |
| 影响 | 结构冗余、入库多一次转换、产物不干净。 |
| 解决方案 | 从 `Chunk` 与 chroma metadata 移除 `kind_comp/char_len/overlap`，保留 `id/doc/section_path/text/rows/start_block/end_block`；`run_chunking.describe` 改为现算 `len(text)`；`run_vectorize` 去掉 `json.dumps(kind_comp)`；`selftest` 适配。 |
| 处理效果 | chunk 字段精简为 7 个；入库只写 `doc/section_path/start_block/end_block`；评估/检索/引用行为不受影响。 |
| 状态 | ✅ 已修 |

### A4.【向量化】chromadb `add()` 空指针崩溃（0xC0000005）
| 字段 | 内容 |
|---|---|
| 问题 | `col.add()` 在**入库条数跨过默认 `hnsw:batch_size=100`** 边界时，chroma-hnswlib 原生库**空指针崩溃**（Windows 弹窗「指令引用了 0x0000000000000000 内存」，无 traceback，缓冲 print 丢失）。已排除：坏向量(NaN/Inf/零)、容量(DEFAULT_CAPACITY=1000)、`hnsw:num_threads=1`。 |
| 影响 | 向量化阶段整批写库必崩，管线在流程三阻塞。 |
| 解决方案 | 建集合时把 `hnsw:batch_size` 设为 **> 本次入库总条数**（`max(1000, len(chunks)+10)`），让单次 add 不触发那次边界刷新（`run_vectorize.py`）。 |
| 处理效果 | 307 / 338 条全部 `add()` 成功 + 可 `query()`。 |
| 状态 | ✅ 已修（改 `run_vectorize.py`；属本机 chroma-hnswlib 兼容坑，已记入「环境选型/踩坑」） |

## D. 已评估 · 未来优化方向（本会话未引入）

### D1. 用 `pymupdf_layout` 做版式/标题提取 —— 实测效果很好，**暂缓引入**
- **背景**：手写字号启发式 `_heading_level` 对「标题以 `！` 结尾 / 标题换行拆分 / 标题与正文合并」无解，且强耦合本公告语料；前述 B3（标题跨行残片）正是这类。
- **实测（2026-08，27 篇）**：`pymupdf-layout` 是 PyMuPDF 1.28 的子模块 `pymupdf.layout`（仅额外依赖 `networkx`，**无需 onnxruntime**，本机可跑）。`pymupdf._get_layout(page)` 输出 `[x0,y0,x1,y1, role]`，role 含 `title / section-header / table / page-header / caption / text / list-item`。27 篇实测：
  - ✅ **把所有拆分标题合并**（如 `…钢铁洪流」来`+`袭` → 一块 `…钢铁洪流」来袭`）
  - ✅ **修好「标题与正文合并」**（6月17日 `…永寂渊主」上线！` 成一块标题）
  - ✅ **识别出 extract 漏掉的以 `！` 结尾标题**（三周年 `…上晶核，放开打！`、第七期 `…获奖名单公布！`）
  - ✅ 未误判假表（`table` 角色 Tb:0）
- **待验证/注意**：① `section-header` **无级别**，需按字号推 L1/L2（阈值重校）；② 块内多行 **CJK 拼接**需专门处理（偶见 `上线 回 路系` 这类怪 join）；③ **真表识别**需一个含真表文档验证（本次都是公告，无真表）；④ 逐页跑模型比纯 PyMuPDF **慢**。
- **决策**：**暂缓引入**——避免过度引入依赖；且切库会**弱化「自研结构分析」**卖点（骨架 Block/切片/溯源仍在，变的只是 PDF 结构识别一步）。
- **未来若启用**：优先用其 `role`→`Block(kind)` 映射（`title/section-header`→heading、`text/caption/list-item`→para、`table`→table），只替换 PDF 结构识别；或仅借用它的「标题识别/跨行合并」一处。**不建议**半自研半借库的混合（两套逻辑并存会冗余）。
- **安装状态**：已 `uv pip install pymupdf-layout`（仅 +`networkx`），**未接入管线**；用时可 `import pymupdf.layout` 后调 `pymupdf._get_layout(page)` 取 role 块。
