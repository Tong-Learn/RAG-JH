## 一、metadata：存什么、为什么 flatten、是否影响检索

### Q1. metadata 一般存什么数据？作者、时间？
**A**：metadata 是**附在 chunk 上的「来源 / 属性」信息**，用于三件事——**溯源**（这段来自哪）、**过滤**（可预筛范围）、**展示**（标注「来源：某文档 §某节」）。它**不参与相似度匹配**。常见字段：来源文档名/UUID、页码、章节路径、chunk 序号、作者、时间/版本、文档类型、语言。
- 本项目存的是：`doc / section_path / start_block / end_block`（溯源 + 结构坐标，因为你没有作者/时间这类字段；2026-08 已去掉 `kind_comp / char_len / overlap`——纯展示/统计/调试用，后段不消费）。

### Q2. metadata 不就是「键值对」吗？和「标量」有什么关系？
**A**：两个层次：
- metadata 是 **dict（键值对）**，有很多 key，例如 `{doc:"示例1", start_block:2, overlap:False}`；
- chromadb 的约束是：**每个 key 对应的 value 必须是「标量」（str / int / float / bool）**，**不能是 list 或 dict**。

所以 `start_block:2`(int)、`doc:"示例1"`(str) 都没问题；但 `section_path` 的值是**列表** `["…","…"]`——**chromadb 不收 list**，才需要 `join` 成**字符串**入库。（2026-08 已移除 `kind_comp` 这个 dict 字段，省去一次 `json.dumps`；`char_len/overlap` 同理移除以简化。）**「标量」约束的是每个 value 的类型，不是「metadata 只能有一个值」。**

### Q3. 主检索不是「query 转向量 → 去匹配 embedding 字段」吗？metadata 过滤、层级过滤是不是无关的？
**A**：**对**。主检索是**查询向量 vs 存储向量**做余弦相似度排名，和 metadata 无关。metadata 是**旁路**：要么做「预过滤」（先限定范围再匹配，属优化），要么做「检索后的溯源标注」。
- 本项目 `query_retrieval.py / run_rag.py / eval_retrieval.py` 的检索都只写 `col.query(query_embeddings=[...], n_results=k)`，**没传 `where=` 做过滤**，只用 metadata 做溯源。
- 所以「不能按层级精确过滤」对你**无关紧要**——它只是理论上的 filter 能力损失，不影响你的管线。

### Q4. 为什么 flatten 后「不能按层级精确过滤」？什么格式才能精确过滤？
**A**：flatten 把 `["一级","二级"]` `join` 成 `"一级 / 二级"`，**层级熔成了一串**。
- **整串精确匹配**可用：`where={"section_path": {"$eq": "一级 / 二级"}}` —— 精确。
- 但 **「某节的所有子章节 / 按层级匹配」**只能用子串 `where={"section_path": {"$contains": "二级"}}`，它是**子串匹配、不锚定层级**，会误配（如有「不二级」也会命中）。

**能精确按层级过滤的格式**（二选一）：
1. **每层拆成独立标量字段**：`sec1="一级"`、`sec2="二级"`，再 `where={"sec1":"…","sec2":"…"}` 逐层精确匹配。缺点：层级深度固定。
2. **换支持嵌套 / 数组 metadata 的向量库**（Qdrant / Weaviate / Milvus / ES），存 `section_path` 为数组 + `$in` / 嵌套过滤——这是**生产主流**。

> chromadb 0.6.3 不支持数组/嵌套，只能走 ① 或接受现状。

### Q5. 「回溯解析」是什么？
**A**：检索命中后，**靠 metadata 里的 `doc + section_path + start/end_block`** 回查 `data/processed/<doc>.jsonl`（那份 Block 列表）或原 chunk，从而找回「这段来自哪份文档、哪个章节、哪些块」。它用于**展示引用 / 标记出处**，同样**不参与匹配**。即「从库中一行 → 找回原 chunk → 再找回原文档/原块」。

### Q6. metadata 样例
**通用（生产常见字段）**：
```python
{
  "source": "s3://bucket/报告.pdf", "doc_id": "doc-abc-123", "page": 7,
  "chunk_index": 3, "title": "公务用车管理规定", "author": "张三",
  "created_at": "2026-08-01", "doc_type": "pdf", "lang": "zh"
}
```

**按本项目切片字段存的 metadata**（chunk → chromadb 行）：
```python
# 原始 chunk 字段
{
  "id": "chunk_000123", "doc": "示例1",
  "section_path": ["公务用车管理规定", "一、适用范围"],
  "text": "公务用车管理规定 > 一、适用范围\n本规定适用于……",
  "rows": [], "start_block": 2, "end_block": 3
}

# 入库后 chromadb 那一行 = {id, embedding, document, metadata}，metadata 被压成标量：
{
  "metadata": {
    "doc": "示例1",
    "section_path": "公务用车管理规定 / 一、适用范围",   # list -> join 成 str
    "start_block": 2, "end_block": 3                    # int
  }
}
```

## 二、embedding 输入长度与 token（MAX_TEXT_CHARS）

### Q1. MAX_TEXT_CHARS 是「防止上下文超出」吗？
**A**：方向对，但要分清两种**长度限制**：
1. **嵌入输入上限（MAX_TEXT_CHARS 防的这个）**：DashScope 嵌入接口**单条文本 ≤ 8192 token**。模型是**按 token 分词**、不是按字符，所以用 `8192 * 4`（假设约 1 token≈4 字符）**粗略换算成字符数**（≈32768 字符）做护栏。
2. **生成模型上下文窗口**（`run_rag.py` 的 chat 模型那个）——那是另一个东西，由上下文长度 + `max_tokens` 控制，和 MAX_TEXT_CHARS 无关。

### Q2. 管道里真会给 chunk 配那么高吗？会不会触发？
**A**：**不会**。切片 `CHUNK_SIZE=300`，单块 ~300 字（带 overlap 也才 300 多，max≈362）。`MAX_TEXT_CHARS=32768` 是它的 **~100 倍**，**永远到不了** → 这段基本是**死代码**。
- 它只是「万一有人绕过 chunker 直接丢超大文本给 embedder」的**通用防御**，而你的管线不存在这种场景。
- 本项目的**修复**：把 `MAX_TEXT_CHARS` 及其 `*4` 魔数**删掉**，`input` **原样发送**，交给 DashScope 按自身 8192 token 上限处理（真超了会报错），不再静默截断。

### Q3. 即便设置了，超出也不提示？
**A**：对。原来的 `t[:MAX_TEXT_CHARS]` 是**静默截断**，超了就砍尾巴、**没有任何提示**——这正是「静默丢内容」的问题（已改掉）。

## 三、向量维度 / dimensions 与 dim

### Q1. 什么是「向量维度」？「模型默认维度」是什么？
**A**：文本 → 嵌入模型 → **由 N 个数字组成的向量**，这个 N 就是**维度**。`qwen3.7-text-embedding` 默认 **1024 维**（每段变成 1024 个 float）。
- **维度很重要**：库里索引按这个维度建，**每条向量必须同一维度**；余弦相似度也在这些维度上算。

### Q2. `dimensions` 参数和 `dim` 属性各干什么？
**A**：两个不同「入口」：
- **`dimensions` 参数** = **「请求」改变输出维度**。传 `dimensions=256`，请求体就带 `"dimensions": 256`（MRL 降维，省内存/提速）——**前提是模型支持**（`text-embedding-v3/v4` 支持；`qwen3.7-text-embedding` 取决于模型）。
- **`dim` 属性** = **「实测 / 验证」**，**不改任何东西**。它发一条探针文本（`"维度探测"`）真调一次模型、数返回几个数字，确认模型到底输出多少维。

**若两者都生效**：`dimensions=256` 让模型输出 256 维；`dim` 去量就量到 256。**`dim` 是来验证 `dimensions` 有没有生效的**（一个配置、一个验证）。

### Q3. 还能改模型输出维度吗？
**A**：**能，但看模型**——支持 `dimensions` 字段（MRL）的模型才行。而且**索引端和查询端必须用同一个维度**：库里全是 256 维，查询时也得请求 256 维，否则查询向量长度对不上、余弦算出错。**用 `dim` 量准，正是为了两边一致。**
- 本项目用**模型默认维度**（1124→实际 1024），二者都没用，直接用 `len(vectors[0])` 量真实维度。已**删掉未使用的 `dimensions` 参数**，保留 `dim` 探测属性。

## 四、chromadb 遥测 / posthog

### Q1. `_silence_chroma_telemetry()` 实现了什么功能？
**A**：**「堵住 chromadb 坏掉的遥测上报」**。chromadb 用 `posthog.capture(用户id, 事件名, 属性字典)`（**老签名**，3 个位置参数）上报匿名使用数据；而 posthog 7.x 把它改成了 `capture(event, *, distinct_id=…, properties=…)`，**`distinct_id` 只能关键字传** → 第 2、3 个位置参数塞进去就抛 **`TypeError`**（在函数体执行前）。
- 该函数把 `posthog.capture` 替换成 **no-op**（`lambda *a, **k: None`），并设 `posthog.disabled=True`，从而消除 stderr 报错、让进程 **exit code=0**。
- **它不碰数据、不影响检索正确性**，纯粹是「治坏掉的上报引发的噪音」。

### Q2. 为什么不直接修 posthog / chromadb 的版本兼容？
**A**：**对，治本应修根因**——我曾先用 monkeypatch 只是「兜底」。**真正的根治**是「把 posthog 装成 chromadb 0.6.3 能配的版本」：
- 已把 posthog **钉回 3.x**（`posthog>=2.4.0,<4.0.0`，本机装到 **3.25.0**）；
- 配合 `anonymized_telemetry=False` 会自动 `posthog.disabled=True`，**无需再 monkeypatch**；
- 原 `_silence_chroma_telemetry()` 已从 4 个脚本**整体删除**。

### Q3. `CHROMA_TELEMETRY_ENABLED` 环境变量有效吗？
**A**：**无效**。chromadb 0.6.3 **源码不读取**这个变量。要用 monkeypatch（已弃用）或**钉兼容的 posthog 版本**（现行方案）。

### Q4. 为什么 chromadb 1.5.x 不行、0.6.3 才行？
**A**：chromadb 1.5.x 在 Windows 上的 **Rust 原生绑定**（`chromadb_rust_bindings.pyd`）在 `add()` 建索引时**必段错误（`0xC0000005`）**。0.6.3 是**最后一代 hnswlib 实现**（C++），且依赖的 `chroma-hnswlib` 在 Windows **只有 cp311 wheel** —— 这就是 `chromadb 1.5.x 不可用`、`0.6.3 + Python 3.11` 为可用组合的根源。

### Q5. 为什么 `EphemeralClient` 冒烟测试会崩？
**A**：chromadb 0.6.3 的 `EphemeralClient.add()` 在本机**段错误（`0xC0000005`）**；而**真实管线用的 `PersistentClient`（`data/chroma`）add/query 正常**。排查/冒烟**请用 `PersistentClient`**，别用内存库。

## 五、运行环境 / 双解释器

### Q1. 为什么之前数据准备/切片用 Python 3.13、向量化用 3.11？
**A**：**向量化必须 3.11**——chromadb 0.6.3 依赖的 `chroma-hnswlib` 在 Windows **只有 cp311 wheel**（3.12/3.13 装不上），且 chromadb 1.5.x（Rust 绑定）在 Windows `add()` 段错误。而早期**解析库（fitz/docx/openpyxl/pptx）装在全局 3.13**，所以数据准备/切片在 3.13、向量化在 3.11，管线被撕成两段。

### Q2. 现在统一了吗？
**A**：**已统一到 `.venv_rag311`（Python 3.11）**。把 `fitz/docx/openpyxl/pptx` 也装入 `.venv_rag311` 后，整条「提取→切片→向量化→检索→生成」**一个解释器一条命令跑到底**，不再分两段。
> 注意：本机 `python` 不在 PATH，统一用 `.venv_rag311\Scripts\python.exe`，别用裸 `python` 或 `py -3.13`。

## 六、embedding 模型选型与同源

### Q1. 为什么 embedding 模型的**名字**前后不一（`text-embedding-v3` vs `qwen3.7-text-embedding`）？
**A**：两者**都是真实模型，但归属不同**：`text-embedding-v3` 是阿里云 DashScope 的经典向量模型；`qwen3.7-text-embedding` 是千问/QwenCloud 的「Qwen3.7-通用文本向量」。本项目**实际用的是 `qwen3.7-text-embedding`**（`.env` / `dashscope_embedder.py` 一致），文档里出现的 `text-embedding-v3` 一律视为**备选/对比**。**别据文档把 `.env` 改成 v3**——否则索引端和查询端会用不同模型、向量不同空间。

### Q2. 为什么「切片必须在前、向量化在后」？
**A**：embedding 是**按每个文本单元**算的，检索要的是**片段向量**；整篇的向量**切不开、也反推不出**各片段向量。所以入库顺序只能是「切片 → 逐块嵌入」。存在「先向量化再定切点」的**语义切分**（按句嵌入、相似度骤降即断层），属第二版增强。

### Q3. 为什么检索/入库必须**同一个 embedding 模型**？
**A**：模型不同 → 向量不在**同一语义空间** → 相似度无意义。所以「查询编码」必须和「入库编码」用**同一个模型、对同一格式文本**。
