# 数据准备方案

> 管线第 ① 步：把源 PDF 经「提取 → 清洗」统一成一套**结构化语料**，供切片使用。

## 1. 整体管线

```
源 PDF（test/*.pdf）
      │
      ▼ ① 提取  extract_pdf（preprocessing/extractors.py）
 [Block, Block, ...]  结构化块
      │
      ▼ ② 清洗  clean_blocks（preprocessing/cleaner.py）—— 规范化 + 去噪 + 丢弃空块
 [Block, Block, ...]
      │
      ▼ 落盘（preprocessing/pipeline.py）
 ├─ *.jsonl           结构化语料（每行一个 Block）—— 真输出，切片器直接读
 ├─ *.md              渲染文本 —— 仅供人眼核对
 └─ manifest.jsonl    来源 / 格式 / 块数 / 字符数
```

**处理对象只有 PDF**：本项目定位为《晶核》游戏官方更新公告，源语料 54 份全部为 PDF，因此
`EXTRACTORS` 仅注册 `.pdf` 一条路径，不引入 Word / Excel / PPT / txt / md 解析库。

### 中间表示：Block（关键设计）

```python
@dataclass
class Block:
    kind: str      # "heading" | "para" | "table"   ← 语义标签
    text: str = "" # heading / para 的正文
    level: int = 1 # heading 级别（1 = 大标题，2 = 章节标题）
    rows: list = field(default_factory=list)   # table 的行（每行是字符串列表）
    page: int = 0  # 页码（1-based），供溯源
```

- `kind` 是**语义标签**，只存在于内存与 JSONL 中，供程序判断；
- `#`、`|` 只是渲染成 Markdown 时的展示符号，反向解析时是"猜结构"的线索——
  程序真正依赖的是 `kind`，因此**不需要从 Markdown 反推结构**。

## 2. PDF 提取策略

核心前提：**能不能识别结构，取决于源格式自身带不带结构**。PDF 只带文本层与字号/加粗等排版信息，
因此标题靠**字号/加粗启发式**、表格靠 `find_tables()` 检测。

### 2.1 行级提取

- 用 `page.get_text("dict")` 逐行取**字号 / 加粗 / bbox**（`_line_info`）。
- 行内与行间拼接规则：**ASCII 之间补空格、CJK 直连**（`_join_para_line_parts`），
  避免中文跨行被压出多余空格（如「这片 厚土」）。
- 页面级统计（`_mode_body_size` / `_estimate_line_h`）：
  - **正文字号** = 按行字符数加权的字号众数（0.5pt 分桶，抗浮点噪声）；
  - **正文行高** = 相邻行 `y0` 差值的正数众数。

### 2.2 标题判定（`_heading_level`）

以正文字号为基准，按**字号比值 + 加粗 + 行长**判定，顺序如下：

| 顺序 | 条件 | 结论 |
|---|---|---|
| 1 | 行长 > 50 | 非标题 |
| 2 | 字号 ≥ **1.35×** 正文 | level 1（**大字号即使以 `！`/`。` 结尾也算标题**） |
| 3 | 以句末标点（`。！？；，,.;`）结尾 | 非标题（仅拦小字号行） |
| 4 | 字号 ≥ **1.15×** 正文且行长 ≤ 30 | level 2 |
| 5 | 加粗且行长 ≤ 25 | level 2 |

标题做**文档级去重**（防每页标题栏重复）；纯序号行（`01`、`1.`）直接丢弃。

### 2.3 视觉行聚类（`_cluster_visual_row`）

**背景**：部分公告把标题排成**逐个字形**（如「常规服」排成 `规` / `常` / `服` 三个独立字形），
且首字 baseline 抬高（实测差 3.9pt），PyMuPDF 会把它们拆成多条 line。
按 `(y0, x0)` 排序时抬高过的首字会排到最前，且不满足「同基线 / 近满行」条件，
标题被割裂成 `规` + `常服`。

**做法**：在重排阅读顺序之前，把满足以下**全部条件**的多条 line 聚成一条视觉行，行内**按 `x0` 重排**后拼接：

| 条件 | 常量 | 排除的误并 |
|---|---|---|
| 两者都是标题候选 | — | 标题与同基线正文 |
| 字号带内相同 | `HEAD_SIZE_BAND = 1.0` | 不同级别混并 |
| 纵向条带重叠 ≥ min(高) × 0.3 | `VISUAL_ROW_OVERLAP_RATIO = 0.3` | 正文相邻行（间距≈20pt 不重叠） |
| x 方向不重叠（≤ 3pt） | `VISUAL_ROW_X_OVERLAP_TOL = 3.0` | 装饰水印的 x 高度重叠副本 |
| 每行 ≤ 2 字 | `VISUAL_ROW_GLYPH_MAX_LEN = 2` | 整词（如 4 字的 `《晶核》`） |
| 结果 ≤ 20 字 | `VISUAL_ROW_MAX_TITLE_LEN = 20` | 重复水印被焊成长串 |

### 2.4 段落合并（`_merge_para_lines`）

公告类 PDF 在 PyMuPDF 里常「一行 = 一个 text block」，若逐行成块会把整句拆成多行。
现按**行间距**合并：

- 阈值 `gap_thr = 行高 × PARA_GAP_FACTOR`（`PARA_GAP_FACTOR = 1.6`，实测正文行距≈20pt、段落间距≈40pt）；
- `y0` 间距 ≤ 阈值的相邻正文行并成**完整段落**；
- **标题与表格先判出并 flush 段落**，绝不并入段落——即只有正文行之间才按间距判段。

### 2.5 标题跨行合并

标题换行（被拆成两行）时按以下条件并入同一条标题：

- 同 level + 字号差在 `HEAD_SIZE_BAND` 内 + `y` 间距 ≤ `gap_thr`；
- 且满足「**近满行**」或「**同基线**」之一：
  - 近满行：行右缘 `x1 ≥ 右边界 − FULL_WIDTH_TOL(6pt)` 或 `≥ 右边界 × FULL_WIDTH_RATIO(0.90)`
    （左对齐标题的换行首行常到不了绝对右缘，故两者取更宽松者）；
  - 同基线：两行 `y0` 差 ≤ `SAME_BASELINE_TOL(2.0pt)`，即同一行被拆成两个 line 对象。

### 2.6 表格

`page.find_tables()` 检测，并用 `_is_fake_table()` 判真伪：

- **单行或单列**视为误报（实测公告中板块标题会被误报成 1×1「表格」）；
- 真表格保留为 `table` 块，并跳过其区域内的正文行；
- 假表格区域的短文本转为 `heading` 候选。

### 2.7 页眉页脚

本管线**不处理页眉页脚**。曾尝试「坐标边距启发式」（丢弃距顶/底 60pt 内的块），
实测会**误删文档标题**（标题 `y≈42 < 60`）且**漏掉文章元数据行**，改用固定正则又会过拟合到当前语料，
故整体放弃，只保留清洗阶段领域无关的页码/独立数字过滤。

## 3. 清洗

按块类型分别处理，三道工序：**规范化 → 去噪 → 丢弃空块**。

### 3.1 规范化（`_normalize_ws`）

| 处理 | 说明 |
|---|---|
| 去 HTML 注释 | `<!-- ... -->` |
| 全角空格 → 半角 | `\u3000` → `" "` |
| 数字/字母与汉字之间的空格去除 | `2026 年` → `2026年` |
| 全角标点前后的空格去除 | `晶珀*100 ，` → `晶珀*100，` |
| 连续空格归一 + 去首尾 | `[ \t]+` → 单个空格 |

### 3.2 去噪（`_is_noise`）

| 类别 | 规则 |
|---|---|
| 页码 | `第X页/共Y页`、`第X页`、独立数字行 |
| 文章元数据行 | 行内含「日期 + 时间」（`META_LINE_RE`）**且**以 `听全文` / `N人` 收尾 **且** 长度 ≤ 35 |

元数据行采用「行内匹配 + 尾标记」，而非锚定行首：来源名（如 `晶核CoA`）常出现在日期之前，
锚定 `^` 会漏判，导致 `晶核CoA`、`听全文` 残留在产物里。该规则不写死来源名。
水印、logo 文字等噪音需按真实文档另行补充。

### 3.3 丢弃空块

- `heading` / `para`：规范化后为空或命中噪音 → 丢弃；
- `table`：删掉全空行；整表为空 → 丢弃。

## 4. 产物与清单

| 产物 | 用途 |
|---|---|
| `data/processed/*.jsonl` | 结构化语料（每行一个 Block），切片器直接读，免重复解析 |
| `data/processed/*.md` | 渲染文本，供人核对提取效果 |
| `data/processed/manifest.jsonl` | 记录来源 / 格式 / 语料路径 / 块数 / 字符数，便于溯源与验收 |

当前语料：54 篇 → **1782 块**（heading 667 / para 1115）。数字见 `metrics.json`。

## 5. 代码结构与运行

```
preprocessing/
├─ extractors.py   # Block 定义 + PDF 提取 + EXTRACTORS 分发
├─ cleaner.py      # 规范化 + 去噪 + 丢弃空块
└─ pipeline.py     # 提取 → 清洗 → 落盘（jsonl + md + manifest）
```

```powershell
# 源 PDF 放入 test/（仓库不携带全量语料）
.venv_rag311\Scripts\python.exe -m preprocessing.pipeline --src test --out data\processed
```

依赖仅 `PyMuPDF`；整条管线统一在 `.venv_rag311`（Python 3.11）下运行
（chromadb 0.6.3 的 hnswlib 仅有 cp311 wheel）。

## 6. 已知限制

- **标题识别是启发式**：依赖字号/加粗梯度与文本层；对**无字号梯度 / 复杂分栏 / 底色标题**可能漏判。
  强装饰版式（逐字排版、重复水印）已有专门处理（见 2.3），但仍属启发式边界。
- **扫描型 PDF 不支持**：无文本层需另加 OCR，当前管线不含。
- **图片 / 公式未抽取**：图内文字与公式需 OCR 或多模态。
- **未做去重**：语料内重复或高度相似的文档当前不做去重，直接进入切片。
- 表格能力已实现，但**当前公告语料不含真表格**，未在真实表格上验证。

## 7. 一句话总结

> 数据准备 = **提取（PDF → 带语义标签的 Block）→ 清洗（规范化 + 去噪 + 丢弃空块）→
> 落盘结构化语料（jsonl）+ 人核对文档（md）**。核心是用 `kind` 承载结构，
> 让切片能按标题边界切、把表格当整体，不丢失语义边界。
